## 1. Architecture and service boundaries

- **Task 1 — Knowledge Brain:** Python/FastAPI service with `/ask`, `/health`, and `/ready`. It retrieves from PostgreSQL/pgvector and returns evidence status, citations, confidence, escalation state, and request ID. Task 1 is the only retrieval/evidence source for the other agents. The README is stale: it describes an earlier milestone and says the answer API/retrieval are not present, while the current source implements `/ask`.
- **Task 2 — Inbox Agent:** TypeScript/Fastify inbox workflow. It classifies email, calls Task 1 through a bounded HTTP client, creates a grounded draft or a safe clarification/escalation draft, and persists review/audit state in memory or PostgreSQL. Review actions do not send mail. Its documented in-memory default is not durable.
- **Task 3 — Meeting-to-Scope:** Python/FastAPI service with a rules or LLM extractor, transcript/requirement/proposal/baseline endpoints, and Task 1-backed feasibility checks. It tracks source segments, change summaries, proposed baseline updates, and review events. Its in-memory default is not durable. Current files are untracked in this checkout.

Services use separate schemas and can each run in memory. Their `.env.example` files consistently point to Task 1 at `localhost:8000` and use port 8080 (Task 2) / 8090 (Task 3). Task 1's example DSN uses localhost:55432; Task 2's example DSN points to the same database but a separate schema; Task 3 leaves the DSN blank and defaults to schema `meeting_to_scope`. Task 1's example selects fake embeddings and its comments incorrectly group Ollama under “key required” even though the following text says Ollama needs no key. Provider/model requirements differ across agents and need one deployment guide.

## 4. Security, persistence, and failure-handling findings

- **Authentication/authorization:** No authentication is evident on state-changing Task 2 or Task 3 API routes. Task 3 review requests accept a caller-supplied `actor`/`approved_by`; without identity verification this value is not proof of reviewer authorization. Task 1 `/ask` is also unauthenticated. These are acceptable only for a local demo bound to a trusted interface; they are deployment blockers for multi-user or internet-facing use.
- **Review and sending:** Task 2 does not send email. It stages reviewable drafts. State transitions reject duplicate terminal review actions in unit tests. Task 3 requires explicit service-level approval for baseline updates and records review events. Neither app currently authenticates that approval.
- **Database:** Task 1/2/3 use separate schemas; Task 3 migration code creates schema and migration ledger before applying sorted SQL migrations. Task 3's migration has a unique `(project_id, content_hash)` transcript constraint and review-event table. Task 2 migration tests are opt-in; Task 1/3 PostgreSQL tests are opt-in. No live migration, persistence, isolation, rollback, concurrency, or restart/recovery check could run because PostgreSQL was unavailable. In-memory mode loses state on restart and must be presented as a demo mode.
- **Task 1 API mismatch:** The current Task 1 exposes `/ask`; `/query`, `/ingestion/run`, `/ingestion/status`, and escalation endpoints from the requirements are absent. Client configurations correctly use `/ask` in current Task 2/3, but the Task 1 README and root requirements should be reconciled.
- **Timeouts/retries:** Task 2 and Task 3 clients use configured bounded timeouts and retry transient network/5xx failures; tests cover timeout, connection, and server errors. Retries are bounded exponential backoff, but repeated POST requests may still duplicate upstream model work; downstream idempotency is not a general request-key guarantee. Task 3 transcript ingest is content-hash idempotent. No live timeout/load/recovery test ran.
- **Error responses/logging:** Task 1 tests assert sanitized 500/503/422 responses without stack traces or secret text. Task 2 tests record degraded KB failures. Task 3 maps domain and store errors, but API tests did not finish. Avoid logging request bodies and provider credentials. The inspected example env files contain placeholders rather than live keys. The checkout contains untracked `_server.*.log` files; they were not modified by this audit and should be inspected for sensitive content before sharing the checkout.
- **Synthetic data:** Task 2 dataset and evaluation cases are explicitly synthetic. Task 3's included transcripts are synthetic/demo artifacts. No production customer data should be inferred from these tests.
- **Duplicate/repeat processing:** Task 2 duplicate review actions are rejected in its in-memory tests; durable store behavior and simultaneous requests were not tested. Task 3 transcript content hash gives repeat-ingest protection in unit tests. Task 1 chunk IDs/indexing are designed for stable upsert behavior, but live database re-index/persistence verification is absent.
- **Repository reproducibility:** Task 3 service, migrations, tests, demo data and M7 report appear as untracked files in the current checkout. This is a material risk: the checked-out feature set is not reproducible from the tracked Git history until those files are deliberately committed or otherwise packaged.

## 5. Evaluation quality and limits

### Task 1

The repository has 29 QA cases and an evaluation runner, but no current measured evaluation report was found. Stored milestone report numbers are verification counts, not model-quality metrics. Confidence is heuristic and not calibrated. A previous live spot-check recorded in Task 2's EVALS.md reported a Task 1 response around 132 seconds and abstention because the small local model could not provide a valid citation-backed answer; that is historical evidence, not a run performed in this audit.

### Task 2

The checked-in raw rules report was generated 2026-10-17 and used the deterministic rules classifier on 79 synthetic classification cases plus small behavioral suites. Thresholds: category accuracy ≥0.60, escalation recall ≥0.70, groundedness ≥0.90, no fabrication =1.00, review correctness =1.00.

- Rules classifier: category accuracy **0.709** (threshold 0.60); urgency accuracy **0.595** (no gate); macro F1 **0.714**; escalation recall **0.848** (threshold 0.70); precision **0.667**. Drafts 4/4, safety 4/4, review 6/6. The stored report passes all gates. Category performance is modest and urgency is weak; precision implies one third of escalation predictions were false positives on this corpus.
- Local LLM report: `llama3.2:1b`, OpenAI-compatible interface, only **8** classification cases; category accuracy **0.25**, urgency accuracy **0.50**, macro F1 **0.131**, escalation recall **0.40**, precision **1.00**. It fails category and recall gates. Behavioral drafts 4/4, safety 4/4, review 6/6 pass, but those suites do not offset classification failures.
- Rules and LLM classification runs use different sample sizes, so compare cautiously. Dataset is 71 labeled synthetic emails plus eight hand-written edge cases; no independent holdout or statistical uncertainty is reported. Perfect behavioral scores are based on four or six hand-authored cases. These are smoke/evaluation checks, not deployment evidence.

### Task 3

No `EVALS.md` or measured quality report exists. The verification report's test count is not an extraction/feasibility quality metric. The included tests are predominantly deterministic rules + fake KB fixtures; no live model benchmark, precision/recall, source-linking error rate, or proposal quality study was available.

Do not combine these unlike metrics into one score or treat passing unit tests as production readiness.

2. PostgreSQL integration tests for all three agents were not run; Docker daemon access failed and no `TEST_DATABASE_URL` was configured.
3. Task 3 M7 implementation files are untracked, so current checkout cannot be recreated from tracked history.
4. State-changing routes lack authenticated identities and authorization checks; actor fields can be caller supplied.
5. Task 1 README and root requirements have stale route/milestone claims; there is no root README or Task 3 README. Setup/startup across three services is not described in one current, tested guide.
6. Task 1 and Task 3 lack actual measured evaluation reports; Task 2 LLM quality is below stated thresholds and its corpus is small/synthetic.
7. Task 1's confidence values are heuristic; no calibration evidence. Task 2 draft validation and LLM quality need stronger coverage before operational use.
8. In-memory modes are non-durable. Persistence, concurrent reviews, migration recovery, backup/restore, and crash recovery remain unverified.
9. Manual Task 1 route probes found requirement-listed routes returning 404. Requirements and implementation need a conscious scope reconciliation.
10. No live end-to-end run was possible; current cross-agent scenario evidence is mock/unit-level.

## 7. Prioritized remediation

### Critical

- Add authentication, reviewer identity, and authorization to all externally reachable state-changing endpoints before any deployment. Record authenticated actor IDs server-side rather than trusting request fields.
- Make Task 3 source files part of the intended repository revision and verify a clean clone can run all services and tests.

### High

- Diagnose and fix the hanging Task 1/Task 3 API tests; rerun every API test and add explicit API-level scenarios for abstention, dependency failure, review, and approval.
- Run isolated PostgreSQL migration/integration suites for all agents, including repeat migrations, persistence across restart, duplicate/concurrent review actions, and recovery after interrupted work.
- Publish a single accurate root setup/run/test guide, reconcile Task 1 routes against the requirements, and correct stale Task 1 README statements.
- Improve Task 2 LLM classifier before using it: the current measured model fails category and escalation thresholds. Keep automation disabled and human review mandatory.

### Medium

- Create measured Task 1 and Task 3 evaluation reports with versioned datasets, a held-out set, source-attribution checks, and clear model/rules provenance.
- Add live-but-safe cross-agent smoke tests using synthetic fixtures and a controllable Task 1 outage; capture request IDs and audit history.
- Harden timeout/retry/idempotency behavior for mutations and document realistic latency budgets; test bounded retries and duplicate requests at service boundaries.
- Inspect the untracked server logs for secrets before distributing the current checkout.

### Low

- Calibrate Task 1 confidence and measure abstention quality; the current confidence score is heuristic.
- Fix Task 1 `.env.example` Ollama key comment and align provider variable names/defaults across agents.
- Add a Task 3 README and explain whether proposal estimate ranges are evidence-based, configured, or illustrative.
